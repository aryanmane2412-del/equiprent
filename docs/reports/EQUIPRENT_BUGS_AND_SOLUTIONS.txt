PROBLEM #001

Problem Name:\
Owner dashboard import does not resolve in project analysis

Category:\
Frontend

Severity:\
High

Location:\
frontend/equiprent_app/lib/features/owner/owner_module.dart:20,49
Target file: frontend/equiprent_app/lib/features/owner/presentation/owner_dashboard_page.dart

What is the problem?\
Dart analysis reports that the OwnerDashboardPage import target does not exist and then reports that OwnerDashboardPage is not a class. The target file is present and analyzes directly, so the import resolution failure is confirmed but its exact cause is not yet isolated.

Why does this happen?\
The analyzer cannot resolve the owner dashboard library when it is imported from owner_module.dart. A stale package/analyzer cache, path resolution issue, or a file-system access problem may be involved. These are possible causes, not confirmed root causes.

What happens if we do not fix it?\
Flutter analysis fails, and the app build may fail when the owner route is compiled.

SOLUTION:\
Run `flutter pub get`, clear only generated Flutter analyzer/build caches if needed, then restore package configuration and analyze the owner module again. If it persists, compare the package root and import path casing on Windows and CI.

CODE FIX:\
The route references `OwnerDashboardPage()` at owner_module.dart:49. Keep the dashboard file and route; correct the import only after reproducing the resolver failure with a clean analyzer session. Do not delete the dashboard.

How to test the solution:
Run `flutter analyze lib/features/owner/owner_module.dart lib/features/owner/presentation/owner_dashboard_page.dart`, followed by full `flutter analyze` and a web build.

Not Fixed

PROBLEM #002

Problem Name:\
Admin finance screens still show mutation controls backed by mock state

Category:\
Security / Frontend

Severity:\
High

Location:\
frontend/equiprent_app/lib/features/admin/presentation/admin_finance_pages.dart:55-71, 88-151
frontend/equiprent_app/lib/features/admin/admin_module.dart:52-105

What is the problem?\
The admin finance UI offers “Issue refund”, “Release all ready”, “Release now”, and payout hold controls. These screens read mock payment/settlement data and can show local demo changes. The backend admin route guard rejects writes, so these controls cannot complete real admin actions consistently with the required read-only role.

Why does this happen?\
The admin screens were built as interactive operations prototypes on mock providers, while the backend now enforces read-only access for platform-admin requests.

What happens if we do not fix it?\
An admin can see controls that appear actionable; clicks may alter demo state or fail with 403, confusing the user and undermining confidence in financial reporting.

SOLUTION:\
Replace admin operations screens with read-only views, remove refund/payout status controls, and present clear read-only records backed by GET APIs. Keep support/finance actions in a separately authorized operational role only if product requirements are changed.

CODE FIX:\
Remove `rowActions` for refund and payout controls and replace demo providers with read-only report providers. Preserve mock fixtures for tests and development until the project owner explicitly requests their removal.

How to test the solution:
Widget-test that admin pages have no write controls. Attempt every former POST/PUT/PATCH/DELETE route as admin and verify HTTP 403 with no database or mock-state mutation.

Status:\
Not Fixed

PROBLEM #003

Problem Name:\
Admin analytics charts display hardcoded demo values

Category:\
Backend / Frontend / Financial reporting

Severity:\
High

Location:\
frontend/equiprent_app/lib/features/admin/presentation/admin_analytics_page.dart:18-105
frontend/equiprent_app/lib/features/admin/presentation/admin_overview_page.dart:32-67

What is the problem?\
Analytics shows literal sample funnel and area numbers and uses MockData for GMV and booking-category charts. The range selector changes the label but does not fetch a date-filtered report. Export is also a “coming soon” action.

Why does this happen?\
The analytics screen is still a design prototype wired to mock data rather than an API provider and SQL-backed report endpoint.

What happens if we do not fix it?\
Admins may mistake demonstration values for real equipment, booking, revenue, or profit data and make incorrect decisions.

SOLUTION:\
Add a read-only report endpoint with validated UTC date bounds. Aggregate customer payments, commissions, refunds, owner settlements and expenses from their authoritative payment/ledger tables without counting rental gross as platform revenue. Connect date presets and custom range inputs to that endpoint and show loading, empty and error states.

CODE FIX:\
Replace `MockData.platformGmv`, `MockData.bookingsByCategory`, the local `funnel` and `areas` constants with API response fields. Retain test fakes only in test code.

How to test the solution:
Use a disposable migrated PostgreSQL database with known ledger entries. Verify each date boundary, no double counting, paise-to-INR display, and reconciliation to ledger totals. Test empty/error/loading UI states.

Not Fixed

PROBLEM #004

Problem Name:\
Several role dashboards still use mock data instead of live API records

Category:\
Frontend / Integration

Severity:\
Medium

Location:\
frontend/equiprent_app/lib/core/mock/
frontend/equiprent_app/lib/features/owner/presentation/owner_calendar_page.dart
frontend/equiprent_app/lib/features/admin/presentation/admin_overview_page.dart
README.md:99,132

What is the problem?\
The project documentation states that role screens still use realistic mock data, and source references confirm mock-backed owner calendar and admin overview screens. Existing API modules elsewhere do not prove those particular screens are live-connected.

Why does this happen?\
The repository is being developed in phases; API adapters and UI prototypes coexist.

What happens if we do not fix it?\
Users can see sample listings, bookings, earnings or operations that do not match the server, and their actions may not persist.

SOLUTION:\
Track each screen’s API integration as a separate migration task. Replace a mock provider only after the corresponding backend endpoint, authorization, loading/error states and workflow tests are available. Keep mock fixtures for widget tests.

CODE FIX:\
For each feature, introduce a repository/provider that calls the existing API client and map the response to the current UI model. Avoid changing the project-wide mock store in one step.

How to test the solution:
Run the screen against a local API and disposable database; verify server changes appear after refresh and failures are presented without fake success messages.

Not Fixed

OVERALL VERDICT
---------------
The backend is already well hardened - better than most apps at this stage.
I found NO critical bug such as SQL injection, auth bypass or a hard-coded
production secret. The weak points are mostly MISSING defence-in-depth layers
(security headers, fail-closed rate limiting, key separation, deployment
defaults). Fix the HIGH items before any public deployment.

Severity: HIGH = fix before going live | MEDIUM = fix soon | LOW = hardening


------------------------------------------------------------------------------
 1. WHAT IS ALREADY GOOD (keep it)
------------------------------------------------------------------------------
 [+] Passwords: Argon2id (OWASP params), constant-time compare, dummy hash for
     unknown users (no timing-based user enumeration).
 [+] JWT: algorithm pinned to HS256, issuer + expiry required, 15 min access
     token, opaque refresh token stored as SHA-256 hash only.
 [+] Refresh-token ROTATION + REUSE DETECTION (whole session family revoked).
 [+] OTP: 6-digit crypto/rand, stored as HMAC (not plaintext), max 5 attempts
     per challenge, hourly/daily caps per phone, same answer for every failure.
 [+] Login lockout per identifier (10 / 15 min) plus per-IP limiter.
 [+] Config refuses to start in staging/production with: dev secrets,
     secrets < 32 chars, dev OTP echo, simulated GPS, sandbox payments,
     localhost CORS, no Redis.
 [+] Payment webhook: HMAC-SHA256 verified with hmac.Equal; empty secret =
     reject; events de-duplicated and retried; raw body signed.
 [+] Uploads: content sniffed (not filename), images re-encoded (strips EXIF
     GPS), size/pixel caps, private storage, HMAC-signed expiring URLs,
     nosniff + attachment headers on download.
 [+] Sensitive IDs (PAN, licence, bank no.) encrypted with AES-256-GCM.
 [+] CORS allow-list (no wildcard), WebSocket origin check, body size limit,
     server timeouts (slow-loris protected), panic recovery, request-ID
     validation, distroless non-root backend image, .env is git-ignored.
 [+] SQL is generated by sqlc (parameterised). The one dynamic query builder
     (discovery search) uses bind args and LIKE-escaping.

 2. FINDINGS - HOW TO FIX
------------------------------------------------------------------------------

[H1] HIGH - docker-compose "app" profile runs the API in DEVELOPMENT mode
     File: docker-compose.yml (x-backend-env: APP_ENV: development)
     Problem: In development mode AUTH_DEV_SIMULATION defaults to true, which
       RETURNS OTP codes / email tokens inside API responses (dev_code,
       dev_token). Anyone who deploys this compose file to a server gets
       a login that can be taken over for ANY phone number just by asking
       for an OTP. Also CORS allows any localhost origin.
     Fix:
       - Never deploy docker-compose.yml. Create docker-compose.prod.yml
         (or Kubernetes manifests) with APP_ENV=production and secrets from
         a secret manager.
       - Make the compose file read APP_ENV from .env, and add a big
         warning comment "LOCAL ONLY".

[H2] HIGH - PostgreSQL is exposed on all interfaces with a known password
     File: docker-compose.yml
       ports: "${POSTGRES_PORT:-5434}:5432"
       POSTGRES_PASSWORD default: equiprent_dev_password
       DATABASE_URL uses sslmode=disable
     Problem: On a laptop on public Wi-Fi, or any server, the database
       (with PostGIS and all KYC data) is reachable from the network with a
       password that is published in your repo / .env.example.
     Fix:
       ports:
         - "127.0.0.1:${POSTGRES_PORT:-5434}:5432"     # bind localhost only
       Production: private network only, strong random password, and
       sslmode=verify-full in DATABASE_URL.

[H3] HIGH - No HTTP security headers on the API
     File: backend/internal/httpserver/router.go (middleware chain)
     Problem: Chain is RequestID > Recovery > Logging > CORS > BodyLimit >
       Errors. Nothing sets HSTS, nosniff, frame-ancestors, referrer policy,
       or Cache-Control: no-store on auth/token responses. Token JSON can be
       cached by proxies/browsers; the API can be framed; HTTPS downgrade is
       possible.
     Fix: add this middleware (new file httpserver/secheaders.go) and put it
       FIRST in r.Use(...):

         func securityHeaders(prod bool) gin.HandlerFunc {
             return func(c *gin.Context) {
                 h := c.Writer.Header()
                 h.Set("X-Content-Type-Options", "nosniff")
                 h.Set("X-Frame-Options", "DENY")
                 h.Set("Referrer-Policy", "no-referrer")
                 h.Set("Cross-Origin-Resource-Policy", "same-site")
                 h.Set("Permissions-Policy", "geolocation=(), camera=(), microphone=()")
                 h.Set("Content-Security-Policy", "default-src 'none'; frame-ancestors 'none'")
                 if prod {
                     h.Set("Strict-Transport-Security", "max-age=63072000; includeSubDomains; preload")
                 }
                 if strings.HasPrefix(c.Request.URL.Path, "/api/") {
                     h.Set("Cache-Control", "no-store")   // never cache API/auth data
                 }
                 c.Next()
             }
         }
       NOTE: the /docs Swagger page needs its own relaxed CSP (see M3).

[H4] FIXED (2026-11-21) - the per-IP limiter on /auth now fails closed in
     production (Rule.FailClosed). CORRECTION: the per-account lockout and OTP
     counters in auth/service.go already returned an error when Redis failed
     (they were fail-closed), so the paragraph below overstated that part.
     Original text: Rate limiter FAILS OPEN, including on login/OTP routes
     File: backend/internal/ratelimit/ratelimit.go (Allow)
     Problem: If Redis is down/slow, every request is allowed. An attacker who
       can knock Redis over (or just wait for an outage) gets unlimited OTP
       requests (SMS-bomb cost) and unlimited password guesses. The per-account
       lockout (lockKey) uses the same store, so it fails open too (lines
       ~355 / ~116-123 of auth/service.go).
     Fix:
       - Add a FailClosed option on Rule; use it for the "auth" rule and for
         OTP/lockout counters (return 503 instead of allowing).
       - Keep fail-open only for the general "api" rule.
       - Alert when "rate limiter unavailable" is logged.

[M1] MEDIUM - Rate-limit key is only the IP; proxy setting is easy to get wrong
     Files: ratelimit.ByIP, config HTTP_TRUSTED_PROXIES (empty by default)
     Problem: Behind a load balancer with the default (empty) setting, EVERY
       user shares the LB's IP -> 20 auth requests/min for the whole country
       (self-inflicted denial of service). If you "fix" it by trusting too
       wide a CIDR, attackers spoof X-Forwarded-For and bypass the limit.
     Fix: set HTTP_TRUSTED_PROXIES to exactly your LB CIDR; add a second
       limiter key per phone/email on /auth/otp/request and /auth/login (the
       per-identifier counters exist - make them fail closed, see H4).
       Add a startup warning when env=production and TrustedProxies is empty.

[M2] WITHDRAWN - CORRECTION: tickets are already domain-separated
     (live.go prefixes the key with "ws-ticket\n"), so this is not a flaw.
     Original (incorrect) text follows. One secret (JWT_SECRET) is reused for WebSocket tickets
     File: backend/internal/app/app.go
       live.NewTickets(cfg.Auth.JWTSecret, cfg.Tracking.TicketTTL)
     Problem: No key separation. A bug in one feature that leaks signatures
       (e.g. ticket oracle) weakens the access-token key as well.
     Fix: derive purpose-specific keys, e.g.
         ticketKey := hkdf(JWTSecret, "ws-ticket-v1")
       or add a separate WS_TICKET_SECRET (validated >= 32 chars like the
       others). Do the same check that STORAGE_SIGNING_SECRET, OTP_SECRET,
       JWT_SECRET, LOOKUP_HASH_KEY are all DIFFERENT values at startup.

[M3] MEDIUM - Swagger UI loads scripts from unpkg.com without integrity check
     File: backend/internal/httpserver/router.go (swaggerHTML)
     Problem: Staging (docs on by default) executes third-party JS with
       "persistAuthorization: true" (bearer token saved in localStorage) and
       "tryItOutEnabled". A compromised CDN = stolen admin tokens.
     Fix: vendor swagger-ui-dist into the binary (go:embed) or add
       integrity="sha384-..." + crossorigin to both tags; keep
       API_DOCS_ENABLED=false in production (already the default);
       set persistAuthorization:false; serve /docs with its own CSP.

[M4] MEDIUM - Public /api/v1/status and /health expose internals
     File: router.go (statusResponse, readiness)
     Problem: Anyone can read environment name, version, commit hash and the
       per-dependency health report -> easier targeted attacks.
     Fix: public /healthz returns only {"status":"up"}; move detailed
       readiness/status behind an internal-only listener or admin role; drop
       commit/environment from the public response.

[M5] MEDIUM - Flutter web: tokens live in browser storage, no CSP
     Files: lib/core/auth/token_store.dart (flutter_secure_storage),
            infrastructure/docker/frontend-web.Dockerfile (nginx config)
     Problem: On WEB, flutter_secure_storage keeps data in localStorage
       (encrypted with a key that sits next to it) - any XSS steals the
       refresh token (valid 30 days). nginx sends nosniff/referrer/frame
       headers but NO CSP, NO HSTS, NO Permissions-Policy.
     Fix (nginx):
         add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;
         add_header Permissions-Policy "camera=(), microphone=(), geolocation=(self)" always;
         add_header Content-Security-Policy "default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https:; connect-src 'self' https://api.YOURDOMAIN wss://api.YOURDOMAIN; frame-ancestors 'none'; base-uri 'self'; object-src 'none'" always;
       Also: shorter refresh TTL for web (e.g. 7 days) or an httpOnly
       SameSite=Strict cookie for the web refresh token; terminate TLS in
       front of nginx and redirect 80 -> 443.
       Use nginxinc/nginx-unprivileged (nginx currently runs as root).

[M6] MEDIUM - CI has no security scanning
     File: .github/workflows/ci.yml
     Fix: add jobs for
         govulncheck ./...            (known-vulnerable Go deps)
         gosec ./...                  (static security lint)
         gitleaks / trufflehog        (secret scanning)
         trivy image / trivy fs       (container + dependency CVEs)
         flutter pub outdated + osv-scanner on pubspec.lock
       Turn on GitHub Dependabot and branch protection (required review +
       required checks). Pin GitHub Actions and Docker images by digest.

[L1] LOW - Android hardening
     File: android/app/src/main/AndroidManifest.xml
     Problem: android:allowBackup is not set (default true -> app data,
       including cached data, can be extracted via adb backup on old
       devices); no network-security-config.
     Fix: android:allowBackup="false" and
       android:usesCleartextTraffic="false"; add certificate pinning for the
       production API host (e.g. dio/http_certificate_pinning) and enable
       R8/obfuscation: flutter build apk --obfuscate --split-debug-info=...

[L2] LOW - Unused CORS header "X-Role" is allowed
     File: httpserver/middleware.go (corsAllowHeaders)
     Fix: remove X-Role (and make sure the server NEVER trusts a role from a
       header - roles must come only from the verified token/DB). X-Org-Id is
       correctly membership-checked in auth/middleware.go.

[L3] LOW - Webhook replay window
     File: payments.go Webhook()
     Note: duplicates are blocked by event id (good). When the event id header
       is missing you fall back to a body hash - fine. Add a check that the
       gateway event "created_at" is within e.g. 15 minutes, and rate-limit
       the webhook route by source IP allow-list of the gateway.

[L4] LOW - Seed/demo data and demo flags
     Files: internal/seed/seed.go (fixed password "Tractor-Rental-2026"),
            DEMO_SKIP_INSPECTION_GATE (allowed in staging)
     Fix: make cmd/seed refuse to run when APP_ENV is staging/production and
       fail if any seeded user exists in a production DB; reject
       DEMO_SKIP_INSPECTION_GATE in staging too.

[L5] LOW - Key rotation not visible
     File: internal/fieldcrypt
     Fix: store a key-version byte with each ciphertext so
       FIELD_ENCRYPTION_KEY can be rotated without a big-bang re-encrypt;
       document the rotation runbook; keep keys in KMS/Secret Manager, never
       in plain env files on servers.

[L6] LOW - Logs contain personal data
     File: loggingMiddleware logs client_ip + user_agent for every request.
     Fix: fine for security forensics, but set a retention period (e.g. 30-90
       days), never log request bodies / Authorization / OTP codes (current
       code does not - keep it that way), and mention it in the privacy policy
       (India DPDP Act).

 6. HOW TO "ATTACK" YOUR OWN APP SAFELY (localhost only!)
------------------------------------------------------------------------------
 Only test systems you own. Start the API locally (APP_ENV=development) and
 try these - each one maps to a finding above.

 (a) Security headers present?            [H3, M5]
       curl -I http://localhost:8080/api/v1/status
     Expect: X-Content-Type-Options, Strict-Transport-Security (prod),
     Cache-Control: no-store.

 (b) Rate limit & lockout                [H4, M1]
       for i in $(seq 1 30); do curl -s -o /dev/null -w "%{http_code}\n" \
         -X POST localhost:8080/api/v1/auth/otp/request \
         -H 'Content-Type: application/json' -d '{"phone":"+919800000001"}'; done
     Expect 429 after the limit. Then stop Redis and repeat: it must still
     block (fail closed) - today it will NOT.

 (c) JWT tampering
     Take a valid access token, change "alg" to "none" or edit the payload
     (sub = another user's UUID), send it as Bearer. Expect 401.

 (d) Refresh-token reuse
     Call /auth/refresh twice with the same old refresh token. Expect the 2nd
     call to fail AND the new token family to be revoked.

 (e) IDOR
     Log in as user A, copy a booking/invoice/chat/file id belonging to user
     B, request it as A. Expect 403/404 on every endpoint.

 (f) Mass assignment
       curl -X PATCH .../users/me -H "Authorization: Bearer <A>" \
            -d '{"full_name":"x","roles":["admin_super"],"status":"active"}'
     Expect 400/ignored.

 (g) X-Org-Id abuse
     Send another organisation's UUID in X-Org-Id. Expect 403.

 (h) Upload attacks
     Upload a .php renamed to .jpg, a PDF with JavaScript, a 50 000 x 50 000
     px PNG (decompression bomb), a zip renamed .pdf. Expect rejection.

 (i) Signed-URL tampering
     Change exp= or key= in a /files?key=..&exp=..&sig=.. link; try ../
     in key. Expect 401/403/404.

 (j) Webhook forgery
       curl -X POST localhost:8080/api/v1/webhooks/payments/razorpay \
            -H 'X-Razorpay-Signature: abc' -d '{"event":"payment.captured"}'
     Expect 401. Replay a valid signed event twice; 2nd = "duplicate".

 (k) Injection
     Search/filter fields with  ' OR 1=1--  , %  , _ , very long strings,
     unicode. Expect normal validation errors, no 500.

 (l) CORS
       curl -i -H "Origin: https://evil.example" localhost:8080/api/v1/status
     Expect NO Access-Control-Allow-Origin header.

 (m) Automated scanners (free)
       OWASP ZAP baseline:
         docker run -t ghcr.io/zaproxy/zaproxy:stable zap-api-scan.py \
           -t http://host.docker.internal:8080/api/v1/openapi.json -f openapi
       Dependency scan:   govulncheck ./...      trivy fs .
       Secret scan:       gitleaks detect
